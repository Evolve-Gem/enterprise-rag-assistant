# 演示脚本 · Demo Script

五个稳定可复现的场景。每个场景都给出：**输入 → 预期行为 → 展示重点 → 可能的意外与应对**。

---

## 0. 演示前准备（3 分钟）

```bash
# 1) 后端（终端 1）
cd backend && uvicorn app.main:app --port 8000
#    看到 "index: 24 documents / 283 chunks" 即为就绪

# 2) 前端（终端 2）
cd apps/web && npm run dev
#    打开 http://localhost:3001
```

**演示前检查清单**

| 检查项 | 期望 | 如果不对 |
| --- | --- | --- |
| 左下角系统状态 | 模型已配置（绿点） | `.env` 里的 `LLM_API_KEY` 没填 |
| 左下角索引状态 | `24 文档 · 283 块` | 点 Documents 页的「重建索引」 |
| 顶部右侧徽标 | 「服务正常 · langgraph」 | `AGENT_ENGINE=auto` 且已装 langgraph |
| Settings 页系统自检 | 无红色项 | 按提示项处理 |

> 💡 演示前先在 **Ask** 页随便问一个问题，把首字延迟（含模型握手）消化掉。
> 之后每个问题大约 4–8 秒，讲了这么多话的间隙刚好。

## 场景 1 · 知识库问答（引用可溯源）

**页面**：Ask

**输入**

```
Rerank 在 RAG 检索链路里解决什么问题？
```

**预期行为**

1. 右侧出现「知识小精灵」和五段进度：理解问题 → 检索知识库 → 阅读知识片段 → 重排序证据 → 生成回答。
2. 约 4–6 秒后返回答案，正文里带 `[1][2][4]` 这样的引用角标。
3. 顶部溯源条显示「已溯源（4 条引用）」+ 延迟 + token 数。
4. 底部列出「来源」chips。

**展示重点**

- **不是引用「文档名」，是引用到 chunk**：角标精确指向被使用的证据片段。
- 答案结尾的「来源」段落是**模型自己写的**，与右侧引用列表应当一致。

**讲这句**

> 「回答里的每个事实后面都有编号，编号不是装饰——它是模型被要求必须标注的，而且后端会校验编号有没有越界。」

## 场景 2 · 引用下钻（解释分数的来源）

**页面**：Ask（承接场景 1）

**操作**：点击答案里的 `[2]`

**预期行为**

右侧滑出抽屉，包含四块内容：

1. **元数据**：来源文档、所属章节、`chunk_id`、文档内序号、字符数、命中分支（关键词/向量）。
2. **检索与排序元数据**：`BM25 关键词分` / `向量相似度` / `RRF 融合分` / `重排分` + 四类名次。
3. **命中词**标签。
4. **被引用的原文片段**（完整 chunk，不只是摘要）。

**展示重点**

- 同一个片段能看到它**在两个分支里各自的排名**——这就是混合检索的意义。
- 抽屉顶部的编号按钮可以横向切换，直接对比 `[1]` 和 `[4]` 的分数差异。
- 回到 Ask 页切到「检索证据」标签，能看到**漏斗**：候选池 283 → 关键词 16 / 向量 16 → 融合 4 → 重排 4。

**讲这句**

> 「排序不是黑盒。这里能看到每个候选片段在每一层的分数和名次，出了问题能定位到是召回的问题还是排序的问题。」

**可能的意外**

- 如果点击角标没反应 → 说明该答案在「生成」步骤失败（未配置 key 时的降级路径），此时正文里不会有编号。改用「引用详情」标签页点击。

## 场景 3 · 客户需求 → 售前方案

**页面**：Solution Studio

**输入**：点击「填入示例客户需求（职业院校知识库）」，或手填

```
某职业院校希望把招生政策、教务规定和学生事务答疑统一到一个知识库，
老师和学生可随时提问，减少重复的人工解答。学校预算有限，希望先小范围试点。
```

**预期行为**

1. 点击「生成售前方案」后显示生成态（小精灵 + 8 章节提示）。
2. 约 10–15 秒后返回：
   - **方案概览**：客户类型=职业院校、行业=教育、解析来源=模型解析、`7/8 章节带引用`
   - **8 个章节**：Executive Summary → Customer Needs → Recommended Architecture → Product Mapping → Implementation Plan → Case References → Risks → Next Steps
   - 每个章节标题右侧标注「含引用」或「无引用依据」
3. 切到「需求解析」标签：核心需求 / 主要痛点 / 关键约束 / 待确认问题 / **检索查询词**。
4. 切到「引用证据」标签：方案里 `[n]` 对应的具体片段。
5. 点「Markdown」或「Word」下载。

**展示重点**

- 「检索查询词」是**需求解析产出的**，不是原始需求——这就是为什么 Agent 的 Tool 执行要排在检索之前。
- 没检索到依据的章节会**显式说明**，不会硬编内容。

**讲这句**

> 「方案生成不是让模型自由发挥，而是拆成：解析需求 → 用解析结果去检索 → 按固定八个章节生成 → 每个章节标注引用。没依据的章节会写出来，而不是编。」

## 场景 4 · Agent 任务执行（可观测）

**页面**：Agent Workspace

**输入**

```
帮我分析当前知识库还缺少哪些售前资料。
```

**预期行为**

1. 顶部概览：`gap_analysis_skill` · `kb_gap_analysis` · 引擎 langgraph · 置信度 99% · 约 6–10 秒。
2. **执行轨迹**标签：8 个节点，其中 `retrieve`、`human_check` 状态为 **skipped**（带原因）。
3. **Tool 调用**标签：`analyze_coverage`，含耗时与摘要。
4. **执行计划**标签：3 步，每步带 rationale。
5. 输出：覆盖情况解读（covered 的类型 + 判定依据 + 补录建议）。

**再加一幕（可选，30 秒）**

把「执行引擎」切到 **native** 再跑一次同样的任务，指出：**节点、顺序、输出完全一致，只有调度器不同**。

**展示重点**

- 「跳过」也是可观测事件，不是静默。
- 置信度和次优意图都暴露出来，路由可解释。
- 两个引擎能现场对比，证明双引擎不是 PPT。

**讲这句**

> 「Agent 的可信度来自可观测性：每一步做了什么、花了多久、调了哪个工具、为什么跳过，都在这里。没有这一步，Agent 就只是个黑盒。」

## 场景 5 · 知识缺口分析

**页面**：Insights → 知识缺口

**预期行为**

- **覆盖总览**：甜甜圈显示覆盖率 45.5%，堆叠条分 covered / partial / missing。
- **分类覆盖明细**（11 类）：
  - ✅ 已覆盖：产品介绍、FAQ、成功案例、行业解决方案、AI / Agent 方法论
  - ⚠️ 部分覆盖：价格/报价、实施流程、售后支持、竞品对比、术语表
  - ❌ 缺失：客户需求模板
- 每一项都能看到 **证据文档名** + **命中的特征关键词** + **判定理由**。
- 底部「建议补充的资料」给出 P0/P1 优先级 + 建议标题 + 责任方。

**展示重点**

- 「缺失」判定是可核对的：点开 `价格 / 报价说明` 会看到它的匹配关键词一个都没命中。
- 覆盖率是**规则算出来的计数**，页面里明确写了「不使用模型打分」。

**讲这句**

> 「这一页回答的是『为什么有些问题永远答不上来』——不是模型不行，是知识资产本身有结构性缺口。而且这个结论可以被逐条复核。」
