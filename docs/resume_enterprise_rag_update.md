## 一、简历中建议替换的项目经历

### 企业知识库 RAG 智能助手 / 售前 Agent 工作流平台（2026.05 - 2026.08）

**Python + Streamlit + FastAPI + DeepSeek API + Markdown/TXT 知识库 + Agent / Skill / Tool 调度 | 项目负责人 / 核心开发者**

- 项目定位：面向企业知识库问答、售前资料查询和客户需求分析场景，独立构建可演示的 AI 工作台原型，将“资料检索 - 需求理解 - 方案生成 - Trace 复盘 - 文档导出”串成完整工作流。
- RAG 基础链路：实现本地 Markdown / TXT 知识库读取、固定长度文本切分、中文关键词与短语匹配检索，并调用 DeepSeek API 基于检索片段生成结构化回答，保留来源文档与匹配分数。
- Agent 工作台：将原有 RAG 问答、售前方案生成和 Agent 分析能力合并为统一“智能工作台”，通过意图识别自动选择 `rag_answer`、`solution_generation`、`kb_gap_analysis`、`agent_optimization` 等 Skill，并在 Trace 中展示“任务识别 - Skill 选择 - Tool 调用 - 结果生成”过程。
- 售前方案生成：针对客户需求自动完成需求解析、资料检索和方案草稿生成，输出客户背景、核心痛点、推荐方案、功能模块、实施步骤、预期价值和参考资料来源。
- 知识库管理：新增知识库管理台，支持文档列表查看、上传、预览、编辑、删除和索引重建；支持 `.md`、`.txt`、`.pdf` 文件管理，其中 PDF 当前仅支持上传与列表展示，暂不参与全文检索。
- 可信展示与导出：优化 Streamlit 页面为“智能工作台 / 知识库管理”双入口，支持检索来源展示、知识库未命中提示、模型通用建议显式标记、Markdown 结果导出和 Agent 执行报告导出。
- 工程意识：使用 `kb_tools.py` 抽离知识库管理工具层，使用 `agent_core.py` 维护 Agent / Skill / Tool 分层；通过 `.env` 管理 API Key，保留 FastAPI 健康检查接口，并持续用编译检查和 Streamlit AppTest 验证页面可用性。

**项目成果：** 项目从早期 RAG 问答 Demo 升级为具备统一入口、知识库管理、可解释 Trace、售前方案生成和结果导出的轻量 Agent 工作流平台，可用于展示 AI 应用落地、ToB 场景理解、资料治理和可解释 AI 工作流设计能力。

## 三、当前项目真实能力边界

### 已经具备的能力

- 统一智能工作台：一个入口承载知识库问答、售前方案生成、知识库缺口分析和 Agent 优化分析。
- 意图识别与 Skill 调度：基于关键词规则识别任务类型，并映射到对应 Skill。
- RAG 基础链路：读取 `.md` / `.txt` 文档，切分 chunks，基于关键词与中文短语规则检索，再调用 DeepSeek 生成回答。
- 售前方案工作流：客户需求输入后，先做需求解析，再检索资料，最后生成结构化售前方案。
- Trace 展示：展示接收任务、识别意图、选择 Skill、调用 Tool、生成结果，以及 Skill 内部执行说明。
- 知识库管理：支持文档列表、上传、预览、编辑、删除和索引重建。
- 结果导出：支持问答结果、售前方案和 Agent 报告导出为 Markdown。
- API Key 安全：通过 `.env` 读取 DeepSeek API Key，不写入代码和 README。
- 后端基础：FastAPI 已有基础接口和健康检查接口。

### 还没有做到的能力

- 目前主检索仍是关键词 / 短语匹配，不是正式向量检索。
- `rag/vector_store.py` 仍是扩展占位，尚未接入 Embedding、Chroma、FAISS 或其他向量数据库。
- PDF 当前只支持上传和列表展示，暂不支持全文解析和参与检索。
- Agent 意图识别是规则路由，不是 LLM Router，也没有置信度评分和追问澄清。
- 没有多用户权限、企业级鉴权、审计日志和持久化数据库。
- FastAPI 还不是完整业务 API 层，核心交互主要在 Streamlit 内完成。
- 没有正式 Eval 测试集，暂时只能通过示例问题和页面测试验证效果。

### 面试中建议这样表述边界

可以说：

> 这是一个面向企业知识库和售前场景的个人项目，目前定位是可演示的轻量 Agent 工作流平台。它已经跑通了知识库读取、切分、检索、DeepSeek 生成、方案生成、知识库管理和 Trace 展示；但我不会把它包装成企业级产品，因为它还没有接入正式向量库、权限系统和评估体系。我的重点是通过这个项目证明自己能把 AI 能力拆成业务流程、工具函数和可解释的执行路径。

不要说：

> 这是一个已经可商用的企业 RAG 系统。

也不要说：

> 已经实现了完整向量检索和企业级知识库。

## 四、讲给元气森林转正面试官的方式

### 30 秒版本

> 这个项目最早是一个企业知识库 RAG 问答 Demo，后来我在实习期间对 AI Agent、工作流和业务分析的理解更清楚了，就把它迭代成一个轻量售前 Agent 工作流平台。现在用户只需要在智能工作台输入问题、客户需求或分析任务，系统会先判断意图，再选择对应 Skill，调用知识库检索、需求解析、方案生成或知识库缺口分析工具，最后把结果和 Trace 一起展示出来。它的价值不是单纯调用大模型，而是把资料来源、执行过程和输出结果串成一个可解释的业务流程。

### 2 分钟版本

> 我做这个项目的原因是，很多企业 AI 应用的问题不是“能不能问大模型”，而是“能不能基于企业自己的资料稳定回答，并且让业务人员知道答案从哪里来”。所以我从企业知识库和售前方案两个场景入手，先实现文档读取、文本切分、关键词检索和 DeepSeek 生成，跑通知识库问答闭环。
>
> 后来我发现，如果页面上把 RAG 问答、方案生成、Agent 工作台拆成很多入口，其实不像真实产品。真实用户只会说“帮我查一下”“帮我生成方案”“帮我分析资料缺口”。所以我把入口合并成“智能工作台”，背后通过意图识别选择不同 Skill：普通问题走 RAG 问答，客户需求走需求解析和方案生成，资料治理问题走知识库缺口分析，项目升级问题走 Agent 优化分析。
>
> 我特别强调 Trace，因为面试官或业务方不只关心结果，还关心这个结果是怎么来的。页面会展示识别了什么意图、选了哪个 Skill、调用了哪些 Tool、检索到了哪些来源。如果知识库没命中，我也不会把模型通用回答伪装成 RAG，而是明确标记“未经过知识库资料验证”。
>
> 这个项目还不是企业级系统，当前没有正式向量库、权限系统和 Eval，但它体现了我对 AI 应用落地的理解：不是堆模型，而是把业务任务拆成工作流，把模型能力放在合适位置，并且保证来源可追溯、过程可解释、输出能复用。

### 和元气森林实习的连接点

可以这样讲：

> 我在元气森林实习后，对这个项目的理解发生了变化。以前我更关注“技术上能不能接 API、能不能生成答案”，现在我会先想业务资料在哪里、使用者是谁、输出要服务什么决策。比如商业分析场景里，有赛道资料、品牌资料、产品明细、行业资讯和内部报告，如果后续做 AI 工作流，核心不是让模型自由发挥，而是要先整理资料、保留来源、设计检索和 Trace，再让模型辅助摘要、对比、报告初稿和问题归因。这个 RAG/Agent 项目就是我在业余时间对这些能力的练习和沉淀。

## 五、面试官可能追问与回答

### Q1：你这个项目和普通 ChatGPT 问答有什么区别？

答：

> 普通 ChatGPT 是直接问模型，我这个项目会先经过知识库检索和任务路由。它会判断用户是在问资料、生成方案、分析知识库缺口，还是分析 Agent 化升级；然后调用对应 Skill 和 Tool。回答时会展示来源文档、匹配片段和执行 Trace。也就是说，我更关注“模型如何嵌入业务流程”，而不是只做聊天。

### Q2：你这个 RAG 是向量检索吗？

答：

> 目前主链路还不是向量检索，而是关键词和中文短语匹配。我有意没有在简历里写“已完成向量检索”。现在 `vector_store.py` 里保留了向量库扩展点，下一步可以接 Embedding 和 Chroma / FAISS。这个阶段我优先做的是业务流程闭环、知识库管理、来源展示和 Trace。

### Q3：如果知识库里没有答案怎么办？

答：

> 我做了显式边界处理。如果检索不到资料，系统会提示知识库未命中；如果用户允许，可以调用大模型给通用建议，但页面会明确标记“未经过知识库资料验证”。我觉得这个边界很重要，因为企业场景不能把模型猜测伪装成内部资料结论。

### Q4：这个项目对元气森林有什么迁移价值？

答：

> 我不会说这个个人项目已经能直接用于公司生产环境，但它的方法可以迁移。比如商业分析中经常要处理赛道资料、竞品信息、产品卖点、行业资讯和历史报告。类似工作流可以帮助团队做资料检索、来源追踪、初稿生成、报告结构化和知识库缺口分析。真正落地时还需要接入公司数据权限、评估机制和人工审核。

### Q5：你在项目里最核心的贡献是什么？

答：

> 第一是把 RAG 问答、方案生成和 Agent 工作台从多个割裂页面收束成统一智能工作台；第二是抽象出 Agent / Skill / Tool 的调度结构，让功能不是堆在 Streamlit 页面里；第三是强调可信边界，比如来源展示、Trace、知识库未命中提示和通用模型回答标记。
