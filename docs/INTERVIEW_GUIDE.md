# 面试指南 · Interview Guide

> 所有回答都基于**真实实现**。凡是没做过验证的部分，都在文中标了「未验证」——
> 面试里被追问细节时，承认边界比编造细节安全得多。

---

## 一、1 分钟介绍

> 这是一个企业知识库智能问答与售前 Agent 工作台，解决我在实习里最耗时的三件事：**找不到资料、说不清依据、补不齐知识**。
>
> 技术上它是一个前后端分离的产品：Next.js 前端 + FastAPI 后端 + LangGraph Agent 运行时。
> 核心是四层检索链路——BM25 关键词 + 向量语义 + RRF 融合 + 重排序，
> 回答里的每条事实都带可点击的引用编号，点开能看到被引用的原文片段和全部检索分数。
>
> 再往上是 Agent 层：Agent 负责意图和计划，7 个 Skill 组织业务能力，10 个 Tool 执行具体动作，
> 每一步的耗时和输入输出都会渲染成时间线。同时提供了检索评测，当前 Hit@4 是 90%、MRR 0.8。
>
> 后端有 159 个测试用例，前端类型检查零错误、lint 零警告、生产构建通过。

## 二、3 分钟介绍

**（1）为什么做）**
我在元气森林做 AI Agent + 商业分析实习，日常是「问题 → 翻资料 → 找依据 → 写结论」。
三个痛点：关键词搜不到语义相近的表述；答案没有引用、别人无法复核；反复答不上来的问题背后其实是知识资产的缺口，但没人统计。
这三件事都不是提示词能解决的，所以我把它做成了产品。

**（2）检索做得比较扎实）**
我把检索拆成四层，每一层都可以单独观测和替换。
中间踩了三个真实的坑：

- 第一版用字符 unigram 做中文分词，导致 `在 / 里 / 解 / 什 / 么` 这些虚词把一篇只顺带提到「问题」的文档顶到 21.95 分，真正定义 Rerank 的文档只有 15.17 分，**根本没进候选**。改成 CJK 二元组 + 停用词表后，三种检索器都把正确文档排到第 1。
- 第二版发现 `召回、Top K、Rerank 与 RAG 检索链路.md` 这个**文件名就是完美匹配**的文档拿到零权重，因为 BM25 只索引了正文。加上「文件名 + 章节路径 + 正文」的字段加权后解决。
- 第三版重排序的覆盖度按词计数，把「顺带提到」和「真正定义」判得一样好。改成 **IDF 加权覆盖度**——最没有信息量的查询词权重降到 0，最稀有的升到 1——「定义」chunk 就稳定排第一了。

**（3）Agent 层是可观测的）**
执行顺序是 理解 → 识别意图 → 制定计划 → 执行 Tool → 检索 → 生成 → 人工确认 → 整理。
这里有一处刻意的偏离：**执行 Tool 排在检索之前**，因为方案生成 Skill 必须先解析客户需求，才能从解析结果里提取检索查询词，直接拿口语化需求去搜召回质量明显更差。
引擎支持 LangGraph 和内置状态机双跑，两者**共用同一组节点函数**，所以行为一致、只有调度不同；LangGraph 运行期出错会自动回退并带回警告。

**（4）效果是可量化的）**
评测中心有 10 条冻结用例，Hit@4 = 90%、MRR = 0.800、Recall@4 = 69.2%。
答案质量**只接受人工评分**，没评分时准确率就是 `null`，不用 LLM 自评。

## 三、高频问题

### Q1 为什么做这个项目？

答「三个具体痛点 + 它们各自需要什么工程手段」。
不要说「想学 RAG」。要说：搜不到 → 需要混合检索；说不清 → 需要引用溯源与编号校验；补不齐 → 需要可计算的覆盖度分析。

### Q2 RAG 是怎么实现的？

四段讲清楚，每段给出**为什么这么选**：

1. **切分**：按 Markdown 标题切段，段落级打包到 `chunk_size`，并携带真实字符 overlap；超长段落按句末边界硬切。每个 chunk 记录**章节路径**，引用里就能显示 `检索链路.md › 5. Rerank｜重排序`。
2. **索引**：BM25 统计 + 向量（默认离线哈希 TF-IDF，可换任意 OpenAI 兼容 embeddings）。
3. **检索**：关键词与向量双分支，RRF 融合，再重排序。
4. **生成**：把重排后的证据编号成 `[1] [2]`，Prompt 明确「编号就是引用命名空间」，生成后做**引用校验**，越界编号从正文剔除并标记 warning。

### Q3 为什么从关键词检索升级到 hybrid？

因为两种检索的**失败模式几乎正交**：
BM25 擅长产品名、缩写、错误码这类精确术语，用户换个说法就召回不到；
向量擅长同义改写，但对稀有专有名词容易漂移。
在本项目的评测集上，`hybrid` 的关键词分支与向量分支**同时命中的比例为 45.6%**，说明两个分支确实在互补，而不是重复劳动。

### Q4 Agent 和 Workflow 的区别？

- **Workflow**：路径预先确定，节点和边在写代码时就定死了。优点是可控、可测试、延迟稳定。
- **Agent**：路径在运行时决定（要不要检索、调哪个 Tool、要不要重试）。优点是灵活，代价是不可预测。

本项目的做法是**混合**：图的结构固定（8 个节点的顺序不变），但**节点内部由 Skill 决定行为**——
`knowledge_overview` 不需要检索，`retrieve` 节点就会被显式跳过并记录成 `skipped` 事件；
`solution_generation` 需要先解析需求再检索，所以 `execute_tools` 排在 `retrieve` 前面。
这既保留了工作流的可控性，又给了业务灵活性。

### Q5 Agent / Skill / Tool 三者是什么关系？

| | 职责 | 数量 | 例子 |
| --- | --- | --- | --- |
| **Agent** | 意图识别、计划、编排、执行、结果整理 | 1 个图 | `AgentGraph` |
| **Skill** | 一类业务能力：决定调哪些 Tool、检索什么词、输出什么形状 | 7 | `solution_generation_skill` |
| **Tool** | 具体动作：执行并返回结构化结果 | 10 | `retrieve`、`analyze_coverage` |

一句话：**Agent 管流程，Skill 管业务，Tool 管动作**。
Tool 不知道自己在为哪个 Skill 服务，Skill 不知道图是怎么调的。

### Q6 为什么需要 rerank？

因为**召回和排序的目标不同**：召回要"别漏"，排序要"别乱"。
初次检索为了不漏，会取比较宽的候选池（本项目默认 `top_k=8`，重排后保留 4）；这一步必然混入噪声。
重排序用更贵的信号（词法交叉特征，或模型打分）对候选重新打分，把真正相关的顶上来。
本项目实测：`RERANK_PROVIDER=off` 时"定义 Rerank 的那个 chunk"排第 3，开 `heuristic` 后稳定进前 2。

**为什么要 ID 加权**：这一个坑值得单独讲（见上文 1 分钟版第 2 点）。

### Q7 chunk 怎么切？

- 先按 Markdown 标题切成 section，并保留标题栈作为 `section` 字段。
- 段内按空行切段落，**整段打包**到 `chunk_size`（默认 500 字符），不会把句子拦腰切断。
- 相邻 chunk 之间带 `chunk_overlap`（默认 100 字符）的真实重叠。
- 单个段落超过窗口时，按 `\n\n → 。→ ！→ ？→ . ` 的优先级找边界硬切。
- 过短的 section 会向后合并，避免索引里塞满"只有标题"的碎片。

**为什么不按固定长度硬切**：硬切会把句子和表格切碎，检索到的片段读起来没有上下文，还会丢失"这段属于哪个标题"这个强信号。

### Q8 Top K 怎么选？

`top_k` 是**召回宽度**，`rerank_top_k` 是**进 Prompt 的宽度**，两个参数解决不同问题：

- `top_k` 太小 → 真正相关的证据进不了候选集，Rerank 也救不回来（Rerank 只能重排已有候选）。
- `top_k` 太大 → 无关内容增加，重排成本上升，Prompt 变长。
- `rerank_top_k` 直接决定 Prompt 长度和 token 成本。

本项目默认 `8 → 4`，并暴露在前端「检索参数」里可以现场调，方便演示「调小能看到漏召回、调大能看到噪声」。

### Q9 citation 怎么做？

1. 重排后的证据按顺序编号成 `[1] [2] [3] [4]`。
2. `format_context()` 把这些编号写进 Prompt，并声明「编号即引用编号」。
3. 生成后 `analyse_grounding()` 从正文反解实际用到的编号。
4. `strip_invalid_citations()` **删掉越界编号**——一个指向不存在来源的 `[7]` 比没有编号更糟，因为它看起来可信。
5. 前端用 React 的 children 遍历把 `[n]` 替换成可点击 chip（不是正则替换 HTML，避免注入），点开右侧抽屉显示原文、章节和四类分数。

### Q10 如何评估 RAG？

分成**两个独立的问题**，绝不混为一谈：

**检索好不好**（确定性计算）：Hit@K、MRR、Recall@K、关键词覆盖。当前 Hit@4 = 90%、MRR = 0.800。
**回答对不对**（人工评分）：correct / partial / wrong。

**为什么不用 LLM 自评**：LLM 打分只是把幻觉换个地方存放，而且不可复现。
本项目没评分时 `answer_accuracy` 就是 `null`，前端显示「未评分」。
评测集是 10 条冻结用例，期望文档由文档名匹配生成，并在备注里标注「建议人工校准」。

### Q11 为什么选择这个技术栈？

- **Next.js 15 + TypeScript**：企业级 UI 需要组件化与类型安全；前端 `types.ts` 手工镜像后端 Pydantic 契约，字段改名会立刻在 `tsc` 阶段暴露。
- **FastAPI**：Pydantic 校验 + 自动 OpenAPI 文档，与 Python 侧的 RAG 生态同进程。
- **Tailwind v4 + 自建 Design Token**：没有引入 UI 组件库，全部组件按 shadcn 风格手写，因为需要严格控制信息密度与明暗两套 token。
- **SQLite + NPZ**：单机演示场景零运维。换 PostgreSQL 只需要改 `DATABASE_URL`，向量存储抽象已经就位。
- **LangGraph**：把 Agent 执行变成可观察的图；同时保留原生状态机兜底，避免一个可选依赖让产品跑不起来。

### Q12 遇到的最大问题？

**「检索看起来能用，但关键文档根本没进候选」**——而且它是静默的。

排查过程：写了一个诊断脚本，把同一查询在 keyword / vector / hybrid 三个分支下的 top-10 连同每一项的分数全部打印出来。
发现 `RAG.md` 因为重复出现「问题」拿到 21.95 分，而目标文档只有 15.17 分。

根因有三个，全部修在检索层而不是提示词层：

1. CJK unigram 让虚词单字参与打分 → 改二元组 + 停用词表
2. 文件名没进索引 → 字段加权（title boost）
3. 重排序覆盖度把稀有词和高频词同等对待 → IDF 加权

修复前后用同一个诊断脚本对照，正确文档从「完全不在榜」变成「三个分支都排第 1」。

**这件事给我的教训**：排序问题不要先怀疑模型，先看打分函数是不是把噪声和信号一视同仁。

### Q13 如果进入生产，还缺什么？

| 缺口 | 现状 |
| --- | --- |
| **用户体系与权限** | 只有演示级共享密码；生产需要按部门/密级过滤检索结果 |
| **pgvector 集成验证** | 代码已实现（建表 + HNSW + 余弦检索），但本机无 PostgreSQL，只有 SQL 构造被单测覆盖 |
| **流式输出** | 当前一次性返回；生产应上 SSE，配合已有的生成态 UI |
| **OCR** | 扫描件 PDF 现在明确报失败，需要接 OCR 才能覆盖 |
| **并发与限流** | 索引是进程内单例且写入加锁，高并发未压测；需要外部缓存 + 限流 |
| **前端 E2E** | 有类型检查/lint/构建与 HTTP 层验证，但缺 Playwright 端到端用例 |
| **可观测性** | 有 Trace 与活动台账，但没接 OpenTelemetry / 集中式日志 |
| **成本控制** | 没有按租户的 token 配额；`RERANK_PROVIDER=llm` 的对照实验也还没做 |

### Q14 这个项目最能体现你哪方面能力？

**把模糊的业务痛点翻译成可验证的工程方案。**
三个痛点分别对应三个可量化的工程目标，而且每个都能被验证：

- 搜不到 → 混合检索 + 检索评测（Hit@4 = 90%）
- 说不清 → 引用溯源 + 越界编号剔除（grounded 标记）
- 补不齐 → 规则化覆盖度分析（covered / partial / missing + 证据文档）

以及一个更基本的习惯：**发现异常先写诊断脚本定位根因，而不是先调参数**。

## 四、被问到不会的怎么办

直接说边界，然后说你怎么验证。例如：

> 「`PgVectorStore` 我实现了完整的建表、HNSW 索引和余弦检索 SQL，但本机没有 PostgreSQL 实例，所以**只在单测里覆盖了 SQL 构造，没有做集成验证**。要上线我会先用 `docker compose --profile pg up` 起一个 pgvector，跑一遍现有的 159 个测试，再补一个「同一语料在 numpy 与 pgvector 下 top-k 一致」的对照用例。」

比「我做过 pgvector」安全得多，而且显得更专业。
