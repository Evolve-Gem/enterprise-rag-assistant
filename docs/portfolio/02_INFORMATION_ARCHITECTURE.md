### P3｜解决方案：为什么是 RAG + Router / Skill / Agent

**核心结论**：*每条痛点都对应一个可验证的工程目标，而不是一个技术名词。*

| 痛点 | 为什么单靠 LLM / 关键词不行 | 本项目方案 | 可验证的指标 |
| --- | --- | --- | --- |
| 找不到 | 关键词匹配不到语义变体；纯向量对稀有专名易漂移——**两种失败模式几乎正交** | **混合检索**：BM25 + 向量双分支 → RRF 融合 → 重排序 | Hit@4 = 90%、MRR = 0.800 |
| 说不清 | 模型自由发挥的引用不可信；指向不存在来源的 `[7]` **比没有引用更糟** | **引用契约**：编号上下文 → 生成 → 反解 → **越界编号从正文删除** | 溯源率 100%、引用可下钻到 chunk |
| 补不齐 | 缺口是「知识资产问题」，不是模型问题，LLM 数不出来 | **规则化覆盖度分析**：11 类资料 × covered/partial/missing + 证据文档 | 覆盖率可逐条复核，**明确不使用模型打分** |

**为什么引入 Agent 而不只做 RAG**：真实用户不会说「请用 RAG 回答」。他会说「帮我查一下」「帮我出个方案」「帮我看看还缺什么资料」。**必须先识别意图，才能选对路径**——这就是 Router / Skill 存在的理由。

**图示**：三行「痛点 → 不行 → 方案 → 指标」，用箭头串联；右下角一个对照图：关键词检索 vs 向量检索的**失败模式正交性**。
**数据点**：Hit@4 90%、MRR 0.800、11 类覆盖、45.6% 双分支同时命中率（证明互补）。
**素材**：🔴 需新绘；数据 ✅ 已有。

### P5｜技术架构

**核心结论**：*检索是一条四层可观测链路——排序不是黑盒，出问题能定位到是召回还是排序。*

| 层 | 组件 | 关键设计 |
| --- | --- | --- |
| ① 索引 | `KnowledgeIndex` | Markdown 标题切 section + 标题栈；段落级打包 500 字符；真实重叠 100 字符；超长段落按句末边界硬切 |
| ② 检索 | BM25 + 向量 | BM25 **字段加权**：文件名 + 章节路径 + 正文（title boost）；向量默认离线哈希 TF-IDF，可换任意 OpenAI 兼容 embeddings |
| ③ 融合 | RRF | **默认 RRF 而非加权求和**——BM25 分与余弦相似度不同量纲，加权需标定，标定参数会漂移 |
| ④ 重排 | heuristic | **IDF 加权覆盖度** + 短语 + 章节 + 密度 |
| ⑤ 生成 | Grounded | 编号上下文 → Prompt 声明「编号即引用命名空间」→ 生成 → **引用校验剔除越界编号** |

**模块化**：分层原则 `api/routes → services → rag / agents`；**RAG 核心不认识 FastAPI，Agent 不认识数据库**。
**可替换性**：`EMBEDDING_PROVIDER` / `RETRIEVER_MODE` / `FUSION_STRATEGY` / `RERANK_PROVIDER` / `VECTOR_STORE` 全部是配置项。

**图示**：
1. 主图：**四层检索链路横向流程图**（Query → 双分支 → RRF → Rerank → 编号上下文 → 生成 → 校验），每层下方标注该层的关键参数与实测延迟。
2. 副图：引用下钻截图（展示同一个 chunk 的四类分数与名次）。
3. 底部：分层依赖方向条（routes → services → rag/agents）。

**数据点**：chunk 500/100 · 召回 Top-8 → 重排 Top-4 · 检索延迟 1.57ms · `schema_version=3`。
**素材**：`docs/images/v3/03-citation-drawer.png`（✅ 已有）；链路图 🔴 待新绘。

> ⚠️ **本页最容易讲错的地方**：不要说「Top 3」。实际是 **Top-8 召回 → Top-4 进 Prompt**，评测按 k=4。

#### 8.2 三个真实踩坑（**全篇最硬的技术证据**）

| # | 现象 | 根因 | 修复 |
| --- | --- | --- | --- |
| ① | 查询「Rerank 在 RAG 里解决什么问题？」时，真正定义 Rerank 的文档**根本没进候选** | CJK **单字**参与 BM25 打分，`在/里/解/什/么` 等虚词让另一篇文档拿到 21.95 分，目标文档只有 15.17 分 | **字符二元组 + 停用词表**；修复后三种检索器都把正确文档排到第 1 |
| ② | 文件名本身就是完美匹配的文档（`召回、Top K、Rerank 与 RAG 检索链路.md`）拿到**零权重** | BM25 只索引了正文 | **字段加权**：文件名 + 章节路径 + 正文（title boost） |
| ③ | 「顺带提到」排在了「真正定义」前面 | 重排覆盖度**按词计数**，高频词与稀有判别词权重相同 | **IDF 加权覆盖度**：最没信息量的查询词权重降 0，最稀有的升到 1 |

**这三条的通用教训**：**排序问题先去查打分函数，不要先怀疑模型。** 三个坑没有一个是调 Prompt 能解决的。

#### 8.3 诚实的局限（**主动写，不藏**）

| # | 局限 | 现状 |
| --- | --- | --- |
| 1 | **移动端** | 390px 下部分页面横向溢出；桌面端 1440/1280/1080 **零溢出** |

## 四、视觉规范

### 4.1 风格定位

**AI / B2B / 企业解决方案 / 技术产品作品集**——参考企业级产品白皮书，不是比赛 PPT、不是课程作业。

**三条硬约束**：
1. **图多于大段文字**：每页文字量控制在 150–250 字（正文），其余交给图、表、数字。
2. **每页只有一个核心结论**：顶部一句话结论，字号最大；其余内容都是它的支撑。
3. **不花哨**：不用渐变背景、不用装饰性插画、不用动画截图。

### 4.2 色彩（克制的企业配色）

| 用途 | 建议 | 说明 |
| --- | --- | --- |
| 主色 | 深靛蓝 / 深蓝灰（如 `#1E3A5F` 附近） | 企业级、可信、不与「红色=涨」混淆 |
| 强调色 | 单一高饱和色（青绿或琥珀），**只用于关键指标与高亮** | 全书**只用一种**强调色 |
| 中性色 | 白底 + 灰阶（`#F8FAFC` / `#E2E8F0` / `#475569` / `#0F172A`） | 高信息密度靠灰阶层次，不靠颜色 |
| 状态色 | ✅ 绿 / ⚠️ 琥珀 / ❌ 红——**仅用于表示真实状态** | 与功能矩阵的 ⚠️/❌ 语义一致 |
| 真实截图 | 保持原色，**不加滤镜、不加边框特效** | 截图本身要看起来像真产品 |

> ⚠️ **本项目截图自带明暗双主题**。作品集若统一用浅色版面，深色截图（`dark-*.png`）只作为**补充证明**出现（如 P6 或 P7），不作为主视觉，避免版面割裂。

### 4.3 字体与排版

| 元素 | 规范 |
| --- | --- |
| 中文正文 | 思源黑体 / 苹方 / 微软雅黑（选一，全篇统一） |
| 英文与数字 | Inter / SF Pro（数字必须突出，用等宽或 tabular 数字） |
| 大数字 | 单独一级字号（建议 36–48pt），配小字标签 |
| 行距 | 1.5–1.6，段间距大于行距 |
| 留白 | **宁可少放内容，也不挤**——企业白皮书的专业感来自留白 |

### 4.4 栅格与版式

- **A4 横向**（适合截图与流程图）或 16:9；全篇统一

### 4.5 图的三条规范
