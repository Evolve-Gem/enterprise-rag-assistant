## 踩坑：`next build` 偶发 EPERM（本机，非项目缺陷）

症状：`uncaughtException [Error: EPERM ... open '<distDir>/trace']`，紧跟 "Creating an optimized production build ..."。
**机制**（读源码定位）：`next/dist/trace/report/to-json.js` 用 `fs.createWriteStream` 写构建 trace
**且没有挂 error 监听** → 写失败即致命。trace 只是遥测，本不该阻断构建。

**证伪了三条假设**：不是文件锁（手工 `openSync(p,'a')` 成功）、不是路径（改 `distDir` 后错误跟着走）、
不是宿主 shim（`NODE_OPTIONS=""` 已确认生效仍失败）。

**可用组合（本日成功 3 次）**：`NODE_OPTIONS="" "C:/Program Files/nodejs/node.exe" node_modules/next/dist/bin/next build`
**并且保留 `.next` 不要先挪走**（挪走反而更容易失败）。备用保险绳：`C:/agents/temp/next-trace-tolerance.cjs`。

**教训**：我一度根据"系统 node 成功过一次"就把根因写成"托管运行时有问题"，紧接着同命令又失败 ——
**单次成功不构成根因**。已在 skill 与 MEMORY.md 更正。

## 测量本身的教训（三次探针写错，产品都是好的）

1. 等 `/售前方案/` → 页面引导文案里本来就有「售前方案」→ 假匹配，截到了未生成状态；
2. 等「本次回答发生了什么」→ 实际标签是「**这次**…」；
3. 找 `^\[\d+\]$` 的引用 chip → 实际 innerText 是纯数字。

**共同点**：把「等待条件」写成会出现在别处的宽泛串。教训是**等待条件必须选只在目标状态出现的字符串**，
并且**报告结论前先自问"我量到的是我以为的那个东西吗"**。
