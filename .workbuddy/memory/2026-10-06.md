## 用户指出的错误（我认）

上一版报告写「390×844 首屏可见三张核心入口卡片」——**错的**。截图里只有第一张完整。

**两处口径错误叠在一起**：
1. 判定用 `rect.top < innerHeight`（元素**顶边**进视口就算可见），而不是 `rect.bottom <= innerHeight`（**完整**可见）。
   一张在 844px 视口里只露出 44px 的卡片会被判为可见。
2. 取元素用 `document.querySelector('a[href="/ask"]')`，命中的是 **`hidden md:grid` 的桌面卡片**。
   隐藏元素 rect = 0×0，而 0×0 **恰好通过** `top >= 0 && bottom <= vh` 判定 ——
   于是「三个入口全部可见」可以完全建立在三个 0×0 盒子上。
3. 我还把 V4.0 的旧结论直接沿用，改动后没重量。

**修正口径**：先按 `width > 2 && height > 2` 排除隐藏元素，再要求
`top >= 0 && bottom <= vh && right <= vw`。作用域也要收（`main h1` —— 否则 `querySelector('h1')` 命中顶栏标题）。

**修正后实测**：390/430/375 三个尺寸下三张入口**全部完整落在首屏**（390 下第三张底边 786 ≤ 844）。

## 两条工具教训（都值得记）

1. **bash 内联 `python -c` 里的反引号会被当命令替换**：我用模板字符串写 `className`，
   bash 把 `` `...${index === 3 ? ...}` `` 吃掉，**静默把 className 写成了 `className={}`**，
   而脚本自己报了 OK。→ **改代码一律用 Edit 工具或脚本文件，不要用 `python -c` 内联**。
   并且写完必须回读验证（我是靠 grep 发现 `className={}` 才捞回来的）。
2. **测量脚本必须先排除隐藏元素**：`display:none` 的元素 rect 是 0×0，
   任何「在视口内」的判定都会假通过 —— 这是假阴性里最危险的一类（报通过但实际没测到）。

### 小记：SSH 包装会话「2 小时后被重置」是复发现象，不是构建失败

V4.1 发布的构建任务（以及 V4.0 发布时的那次）都出现同一个形态：
用 SSH 后台跑 `docker compose build`，**构建本身在 ~10 分钟内就完成了**，
但包装用的 SSH 会话会一直挂着，满 **2 小时**后被对端
`Read from remote host ...: Connection reset by peer` 断开，
于是脚本里的 `echo "BUILD_EXIT=$?"` 那行**从来没打印出来**。

**两次都不是构建失败**。判据是「不要只看包装脚本的输出，要看它产出的东西」：

1. 服务器构建日志结尾有没有 `web Built` / `naming to ...`；
2. `docker images` 里镜像是否出现、created 时间对不对；
3. 能不能 `docker run --rm --entrypoint sh <img>` 进去读到 `.next/routes-manifest.json`；
4. 用它起的容器是否 `Up (healthy)`。

V4.0 与 V4.1 两次都满足这四条，所以两次都判为成功。

**下次怎么做更省事**：构建这类长任务不要用「SSH 保持前台」的包装方式，
直接把输出重定向到服务器文件，然后在**另一条** SSH 里读日志 / 查镜像即可。
